Sharding Principles in System Design

1. Why Sharding?

When a database exceeds single-server CPU, IOPS, or storage capacity, sharding splits data horizontally across independent instances so reads and writes scale linearly.

2. Partition Key Selection

A good shard key ensures uniform distribution. Poor shard keys cause "hot spots" where 90% of traffic hammers a single shard node.

3. The Scatter-Gather Penalty

Queries without the shard key (e.g. SELECT * WHERE status = 'active') must query all shards in parallel and merge results, which increases tail latency.

System Design Architecture Takeaways

1. The Database Crash Anti-Pattern

Hitting PostgreSQL directly with 50,000 concurrent UPDATE items SET stock = stock - 1 WHERE id = 1 causes row-lock contention and exhausts connection pools, taking down the entire database.

2. Redis Atomic Decrement + Lua Scripting

In-memory Redis handles 100k+ ops/sec. Using DECR in Redis evaluates in sub-millisecond time. Once stock reaches 0, excess requests are rejected with 409 Conflict without touching SQL!

3. Decoupled Message Queue Persistence

The 10 lucky buyers are pushed to a RabbitMQ queue, letting background workers write to PostgreSQL at a safe, throttled rate.

1. Nginx Layer 7 Load Balancing

Nginx acts as the front-door reverse proxy on port 8000. It distributes incoming HTTP requests across the 3 API Gateway replicas using Round-Robin algorithms:

upstream gateway-cluster {
  server gateway-1:3000;
  server gateway-2:3000;
  server gateway-3:3000;
}

2. API Gateway Pattern & Path Rewriting

The API Gateway decouples clients from microservice topology. Using express-http-proxy, it strips path prefixes and attaches telemetry headers:

/auth/health ➔ auth_service:3001/health
/products/health ➔ product_service:3002/health
/orders/health ➔ order_service:3003/health

3. Centralized CORS & Security Boundary

Without an API Gateway, every microservice must manage its own CORS headers, rate limiting, and JWT validation. The API Gateway centralizes CORS and preflight OPTIONS handling in one single layer.

4. Microservice Decoupling & Independent Scaling

Each service (Auth, Product, Order) runs in isolation. If Product Service experiences high traffic, we can scale it independently without modifying client endpoints or redeploying Auth.
